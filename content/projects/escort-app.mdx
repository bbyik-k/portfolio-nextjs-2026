## 📌 프로젝트 개요

- 로봇이 ==목적지까지 길안내==를 하며, 실시간 상태에 따라 사용자에게 ==음성 및 화면 안내==를 제공하는 경비 로봇 전용 서비스입니다.
- 이동 중 로봇의 ==실시간 위치와 상태== (대기, 이동, 도착, 혼잡, 일시정지, 경로 장애 등)를 UI로 ==직관적으로 표현==하며,  
  상황에 맞는 음성 안내를 함께 제공하여 보다 ==명확한 에스코트 경험==을 구현하였습니다.
- 로봇이 에스코트를 수행 중일 때는 메인 화면 이동 및 기타 콘텐츠 이용이 제한되며,  
  자동 복귀 이후에 정상적으로 사용할 수 있도록 설계하여 ==콘텐츠 안정성==을 높였습니다.
- 이동 시작, 일시 정지, 목적지 변경, 원위치 복귀 등의 이벤트 상태는 앱 전역으로 관리되며,  
  UI 콘텐츠 뿐 아닌 ==미들웨어에도 상태를 전달==하여 로봇 ==하드웨어의 움직임을 제어==합니다.
- 관리자 모드에서는 지도 ==UI를 통해 목적지 좌표를 직접 설정==할 수 있도록 구성하여 ==관리자 편의성==을 높였습니다.

## 🧑‍💻 주요 기여

- 에스코트 기능의 기획에 참여하고, 프론트엔드 개발을 [[단독으로 담당]]하였습니다.
- 신규 콘텐츠의 성공적인 시연 및 [[상용화]]를 이끌었습니다.
- 로봇 이동 중 발생하는 다양한 상태를 정의하고, 각 상태에 따라 UI와 음성 안내가 자연스럽게 전환되도록 [[상태 기반 UI 구조]]를 설계하였습니다.
  - [[MVC 구조]]를 기반으로 UI와 로직을 분리하고, 각 상태의 변경 및 추가가 용이하도록 [[State 패턴]]을 적용하여 다양한 [[상태를 관리]]하였습니다.
  - 로봇 상태에 따라 분기되는 다양한 로직을 단순화하고, 결합도를 줄이기 위해 [[Facade 패턴]]을 적용하였습니다.
- 상황에 맞는 [[TTS]] (Text-to-Speech) 음성 안내를 실시간으로 동기화하여,  
  사용자에게 [[명확한 안내]]가 전달되도록 구현하였습니다.
- 로봇의 현재 위치 정보를 [[WebSocket]] 기반으로 수신하고, 지도 UI 상에 위치를 동적으로 반영하는 기능을 개발하였습니다.
- 전체 기능에 대해 반복적인 [[테스트와 리팩터링]]을 거쳐, 현장 시연에서 [[안정적]]이고 [[완성도]] 높은 결과를 도출하였습니다.
- 해당 프로젝트는 경비 로봇 [[서비스를 확장되는 계기]]가 되었으며,  
  이후 2년간 총 14개 고객사 건물에 도입되어 [[비즈니스 모델로 안착]]하는 데 기여하였습니다.

## 🔧 기술 선택 및 설계 고민

### 문제 상황

- 에스코트 기능은 대기, 이동, 혼잡, 도착, 일시정지, 경로 장애 등
  ==수십 개의 상태==를 실시간으로 처리해야 했습니다.  
  각 상태마다 UI 화면 구성, TTS 음성 안내, 미들웨어 통신이 모두 달라졌고,
  초기에는 상태값을 단일 변수로 관리하며 if-else 분기로 처리했습니다.

- 상태가 늘어날수록 ==분기 로직이 복잡==해졌고, 같은 상태 확인 로직이
  UI, TTS, 미들웨어 각각에 중복으로 흩어지기 시작했습니다.  
  특히 [[타이머 기반 이벤트]]가 문제였습니다.  
  목적지 도착 후 자동 복귀, 장애물 감지 후 TTS 안내 -> 대기 -> 복귀로 이어지는 로직이
  서로 충돌하며 ==예상치 못한 동작==이 반복됐습니다.

### 해결 방법

- GitHub, Stack Overflow, Reddit 등 5개 이상의 플랫폼에서
  30개 이상의 오픈소스와 레퍼런스를 직접 분석하며  
  [[MVC]], [[State]], [[Facade]] 패턴을 학습하고 적용했습니다.
  - [[MVC 구조]]로 UI(View)와 상태 로직(Model)을 분리하여 상태 변경이 화면 렌더링 로직에 독립적으로 작동하도록 했습니다.
  - [[State 패턴]]으로 각 상태를 독립 객체로 정의하여 상태 추가 및 변경이 다른 상태에 영향을 주지 않는 구조를 확보했습니다.
  - [[Facade 패턴]]으로 상태 전환 시 UI 업데이트, TTS 제어, 미들웨어 통신을 하나의 진입점에서 처리하여 결합도를 낮췄습니다.

- 패턴 도입 이후 ==수정 범위가 명확==해졌고, 타이머 이벤트 간 충돌 문제도 해소되었습니다.

## 🔥 트러블슈팅

### 상태 증가로 인한 설계 붕괴 → 재설계

- 레퍼런스 없이 처음부터 설계하는 신규 프로젝트였습니다.  
  초기 구조로는 상태가 늘어날수록 에러가 반복됐고, 결국 ==설계 단계부터 다시 잡아가는== 결정을 내렸습니다.  
  뒤늦은 재설계였지만, 패턴을 학습하고 적용하면서 이후 상태 추가와 수정이 훨씬 수월해졌습니다.

### 실제 환경과 테스트 환경의 차이

- 본사 공간만으로는 로봇이 실제로 이동하는 환경을 재현하기 어려웠습니다.  
  하드웨어 설계팀이 있는 더 큰 건물 복도로 출근해 ==밤샘 테스트==를 진행했고, 실제 도입 현장은 규모가 훨씬 커서 예기치 못한 이벤트가 다수 발생했습니다.  
  시연 전날까지 반복 테스트와 수정을 이어가며 안정성을 확보했고, ==최종 시연을 성공적으로 마쳤습니다.==
